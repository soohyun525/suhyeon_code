# 큐피트 — 설계 문서

내 AI 에이전트가 상대의 에이전트와 대화해서 잘 맞는 사람을 찾고, **첫 데이트의 시간과 장소까지 잡아오는** 앱.
경로: `/cupid` · 코드: `src/lib/cupid/`, `src/app/cupid/`, `src/app/api/cupid/match/`

## 2. 원칙 1 — 상태 머신을 명시적으로

암시적 상태(흩어진 boolean, "지금 어느 단계지?")를 없애고 표 두 개로 만들었다. 둘 다 `src/lib/cupid/machine.ts`.

### 2-1. 성사 과정 (후보 한 명당 하나)

```
discovered ─HELLO→ screening ─SCREEN_PASS→ exploring ─FIT_OK→ scheduling ─AGREE→ awaiting_owner
                       │SCREEN_FAIL            │FIT_LOW          │ ↺ PROPOSE/COUNTER     │ ↺ RESCHEDULE
                       ▼                       ▼                 │NO_OVERLAP             │MY_APPROVE
                     no_fit                  no_fit              ▼                       ▼
                                                               no_slot            awaiting_partner
                                                                                    │PARTNER_APPROVE → confirmed
                                          awaiting_owner ─MY_PASS→ declined ←PARTNER_PASS─┘
```

- 에이전트 구간: `discovered` ~ `scheduling`. 사람 구간: `awaiting_owner` 이후.
- **불변식: `confirmed`는 `MY_APPROVE`와 `PARTNER_APPROVE`를 모두 거쳐야만 도달한다.** 에이전트는 제안까지만, 확정은 사람 둘이. `scripts/verify-cupid.ts`가 모든 경로를 탐색해서 확인한다.
- 표에 없는 전이는 예외. 모든 상태에서 종료 상태로 갈 수 있다(막다른 길 없음) — 이것도 점검한다.

| 관점 | 이 결정이 주는 것 |
|---|---|
| UX | 진행 단계 표시줄과 상태 칩이 표에서 그대로 나온다. "왜 멈췄는지"가 항상 한 문장으로 남는다. |
| DX | 새 단계를 넣으려면 표 한 줄. 화면은 `applyOwnerEvent` 하나로만 상태를 바꾼다. |
| AX | 에이전트 메시지마다 "직후 상태"가 붙는다. 에이전트가 할 수 있는 일과 없는 일(확정)이 표로 고정된다. |

### 2-2. 화면 흐름

`landing → onboarding → briefing → dispatching → watching → results ⇄ proposal`
로딩과 에러는 플래그가 아니라 상태다 (`dispatching`, 실패 시 `FAILED → briefing`).

## 3. 원칙 2 — 오픈 소스 비교 후 시작

GitHub 검색으로 비교했다. (이 세션은 다른 저장소의 코드를 열 수 없어서 **검색 결과의 설명 + 공개된 A2A 규격 지식**으로 비교했다. 코드 수준 비교는 아니다.)

| 프로젝트 | 접근 | 가져온 것 / 안 가져온 것 |
|---|---|---|
| Google A2A 프로토콜 (`themanojdesai/python-a2a` ★1007 등) | 에이전트 카드로 자기소개, 작업(Task)에 명시적 생명주기 | **가져옴:** 공개 카드(`AgentCard`) + 명시적 생명주기. **안 가져옴:** JSON-RPC·HTTP 전송 — 아직 실제 상대 서버가 없다. |
| `geeks-accelerator/in-bed-ai` ★26 | 에이전트가 API로 가입·스와이프·매칭·채팅 | 스와이프 대신 "조건 확인 → 점수 → 일정"으로 바로 간다. 목표가 채팅이 아니라 첫 데이트라서. |
| `goeldivyam/truematch`, `ttloai/lovcierge` | 에이전트끼리 대화하는 데이팅 네트워크 / 컨시어지 | 같은 방향. 우리는 "확정은 사람 승인"을 상태 머신 불변식으로 못박았다. |
| LLM 협상 시뮬레이터들 | LLM이 제안·역제안, 비공개 조건 보유 | **가져옴:** 비공개 조건, 제안/역제안. **바꿈:** 결정은 코드가, LLM은 말투만 (지어낸 날짜 방지). |

**핵심 설계 결정: "결정은 코드, 말은 LLM".** 통과 여부·점수·시간·장소는 `engine.ts`의 결정적 코드가 정한다. Claude(`voice.ts`)는 대사 문장만 다듬고, 줄 수가 다르면 버린다. API 키가 없어도 앱은 똑같이 동작한다.

### UI — 당근 Seed Design

화면의 버튼·칩·입력칸·배지·알림은 당근의 [Seed Design](https://github.com/daangn/seed-design) (`@seed-design/react`, `@seed-design/css` 3.3.0, Apache-2.0) 컴포넌트다: `ActionButton`, `Chip.Toggle`, `Chip.RadioRoot/RadioItem`, `TextField`, `Badge`, `Callout`. 색·모서리·선은 전부 Seed 토큰(`--seed-color-*`, `--seed-radius-*`)을 쓴다. 색은 회색 단계와 브랜드색 하나(블러시 핑크 `#FFA3BF` — Seed의 브랜드 토큰을 `tokens.css`에서 다시 선언, 분홍→복숭아 그라데이션 사용), 글꼴은 Pretendard. 브랜드 전략은 [CUPID_BRAND.md](CUPID_BRAND.md), 살아 있는 디자인 시스템은 `/cupid/system`.

- **배경:** Three.js(`Scene.tsx`). 배경을 채우던 점 그물은 빼고, 분홍 점 두 개만 남겼다. 이 두 점이 "나"와 "상대"이고, 진행할수록 가까워지며 점선으로 이어진다. 읽는 화면에서는 숨기고, 에이전트가 대화 중일 때와 확정 순간에만 나타난다.
- **스크롤 효과:** 첫 화면(`Landing.tsx`)은 GSAP ScrollTrigger — 제목 등장, 숫자 시차 이동, 대화가 한 줄씩 또렷해짐, 도장 찍힘, 가로로 흐르는 문장. 스크롤 진행도가 3D 카메라도 움직인다(`stage.ts`).
- **배치:** 카드 나열 대신 가는 선으로 나눈 질문지·장부·대본 형태. PC는 왼쪽 고정 제목 + 오른쪽 내용 2단, 폰은 1단.
- 움직임 줄이기 설정이면 스크롤·등장 효과를 끄고 3D는 정지 화면으로 그린다.
- 이전에 시도했다가 뺀 것: 직접 만든 글래스 CSS, OpenGlass UI(React 18에 바로 붙었지만 색·글꼴이 맞지 않았다).

Saju 전역 스타일과의 충돌은 세 군데서 막았다: `globals.css`의 `input/select/label` 선택자 4개에 `:where(:not(.cq *))`, 구름 장식은 `body:has(.cq)`에서 끔, 큐피트 쪽 버튼 초기화는 우선순위 0(`:where`)으로.

요청받지 않아서 만들지 않은 것: 계정·로그인, 실제 사용자 간 네트워크, 장소 예약 연동, 결제, 알림.

## 5. 원칙 5 — CI 감사 보고 (변경 없음)

이 저장소에는 GitHub Actions 워크플로가 없고 실행 기록도 0건이다(API로 확인). 최근 150회 실행의 대기/설정/실행 시간과 가장 느린 5개 작업은 **측정할 데이터가 없다.** 아무것도 변경하지 않았다. 현재 검증은 로컬 명령 3개다: `npm run test:cupid`, `npm run test:saju`, `npm run build`.

## 6. 원칙 6 — 다시 시작해도 남길 것

기존 저장소는 Saju(사주) 앱이다. 같은 목표로 오늘 다시 시작해도 남길 것만 재사용했고, 아무것도 삭제하지 않았다.

- **남김·재사용:** 사주 궁합 엔진(`saju/compat.ts`) → 케미 점수의 20점. 요청 제한(`ratelimit.ts`), "키 없으면 대체 응답" 패턴, Next.js 구조.
- **건드리지 않음:** Saju 화면(`/`, `/compare`), 결제, 기존 스타일(`globals.css`). 큐피트 스타일은 `.cq` 아래로 격리.
- **새 앱 안에서 남길 핵심:** 두 상태 머신 표, "결정은 코드/말은 LLM", "확정은 사람" 불변식, 비공개 정보 최소 공개.

## 7. 구조

```
src/lib/cupid/
  machine.ts    두 상태 머신 표 + transition()
  types.ts      프로필, 에이전트 카드, 메시지, 제안
  engine.ts     후보 찾기 → 조건 확인 → 점수 → 일정 조율 (서버 전용)
  owner.ts      사람 단계 이벤트 적용 (브라우저용)
  validate.ts   화면·API 공용 입력 검증
  voice.ts      Claude로 대사 다듬기 (선택)
  personas.ts   데모 후보 8명
src/app/api/cupid/match/route.ts   POST {profile} → {courtships, voiced}
src/app/cupid/                     page.tsx(앱 화면) · Landing.tsx(첫 화면, GSAP) · Scene.tsx(Three.js) · stage.ts · cupid.css
scripts/verify-cupid.ts            상태 머신·엔진 자체 점검
```

첫 만남 적합도(100): 가까워지는 속도 25 · 다툼과 연락 15 · 원하는 방향 20 · 속마음 20 · 사랑의 언어 10 · 함께할 거리 10. 프로필 뒤에 깊은 대화(`interview → analyzing → insight`)가 있고, 본인만 보는 연애 심리 결과(속마음·애착 유형·사랑의 언어)를 보여준다. 50점 이상이면 일정 조율로 넘어간다. 사주는 점수에서 빼고 재미로만 보여준다. 근거와 원칙은 [CUPID_PSYCHOLOGY.md](CUPID_PSYCHOLOGY.md).

## 7-1. 인스타그램으로 시작하기

가입 첫 화면은 질문 12개가 아니라 **인스타그램 아이디 한 칸**이다. `landing → connect → reading → persona → onboarding`.

1. `connect`: 본인 아이디 입력 (또는 "직접 입력할게요"로 건너뜀).
2. `reading`: `POST /api/cupid/insta` — 공개 게시물의 글·해시태그를 가져온다.
3. `persona`: 취향 유형 카드("아침 공기 수집가"), 잘 맞는 사람 한 줄, 읽은 근거, 공유 버튼.
4. `onboarding`: 관심사·가치관·데이트 스타일·말투가 미리 채워진 채로 열린다. 고칠 수 있다.

- **가져오기** (`insta.ts` `fetchFeed`): `APIFY_TOKEN`이 있으면 수집 서비스(Apify instagram-profile-scraper)로 실제 계정을 읽는다. 없으면 내장 예시 피드 3개 중 하나를 쓴다(화면에 "예시 데이터"로 표시). 인스타그램은 개인 계정용 공식 API가 없어서 이 길을 택했다 — 약관상 허용된 방식이 아니고 막힐 수 있다.
- **읽어내기** (`readTaste`): 낱말 사전으로 세는 결정적 코드. 결과는 `types.ts`의 허용 목록 안에서만 나온다.
- **하지 않는 것:** 남의 계정 분석을 권하지 않는다(문구는 "본인 계정만"). 사진·위치는 읽지 않는다. 읽은 글은 저장하지 않는다. "무의식·상처·진단" 같은 심리 표현은 만들지 않는다(자체 점검에 포함).
- **남은 문제:** 본인 계정인지 확인하지 않는다. 카드에 "본인 확인 전"으로 표시만 한다.

## 8. 알려진 한계

- 상대는 전부 가상 인물이고, 상대의 승인은 자동이다.
- 장소는 "유형"까지만 정한다. 실제 가게 예약은 하지 않는다.
- 실제 인스타그램 읽기(`APIFY_TOKEN` 경로)는 토큰이 없는 환경에서 만들어져 **한 번도 실행해 보지 못했다.** 응답 형식은 서비스 문서 기억에 의존했다.
- Claude 대사 다듬기는 API 키가 없는 환경에서 만들어져 **실제 호출로 검증하지 못했다.** 실패하면 기본 대사로 돌아가도록만 되어 있다.
